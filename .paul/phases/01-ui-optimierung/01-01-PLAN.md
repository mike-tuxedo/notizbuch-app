<acceptance_criteria>

## AC-1: Safe-Areas respektiert
```gherkin
Given die App läuft auf einem Gerät mit Notch oder Home-Indicator (z. B. iPhone)
When der Nutzer die App im Standalone-PWA-Modus oder im Browser öffnet
Then liegen Topbar, Sidebar-Footer und Pagebar nicht unter Notch / Status-Bar / Home-Indicator
And die Canvas-Zeichenfläche füllt den verfügbaren Raum ohne in unerreichbare Bereiche zu rutschen
```

## AC-2: Mobile-Topbar einzeilig + Farb-/Größen-Trigger schwebend
```gherkin
Given die App läuft auf einem Mobile-Viewport (Breite ≤ 768 px)
When der Nutzer die App öffnet
Then ist die Topbar genau eine Zeile hoch (= --toolbar-h)
And die Buttons #btn-mobile-color und #btn-mobile-size sind absolut positioniert rechts oben, direkt unterhalb der Topbar (außerhalb des Topbar-Flusses)
And sie überlagern keine Tools der Topbar
And sie respektieren `env(safe-area-inset-right)`
```

## AC-3: Touch-Targets ≥ 44 × 44 px
```gherkin
Given die App läuft auf Mobile
When der Nutzer einen interaktiven Button antippt (tool-btn, footer-btn, page-btn, bg-btn, nb-add-btn, nb-list-Eintrag)
Then beträgt die Hit-Fläche mindestens 44 × 44 CSS-Pixel
And der Button reagiert zuverlässig ohne Fehl-Tipps auf Nachbarn
```

## AC-4: Text-Kontrast WCAG AA
```gherkin
Given das Dark-Theme ist aktiv
When ein Element mit color: var(--text-dim) oder var(--text-faint) gegen var(--bg) gerendert wird
Then beträgt das Kontrast-Verhältnis mindestens 4.5:1 (für reguläre Texte)
And mindestens 3:1 für UI-Komponenten und große Texte (≥ 18px regular oder ≥ 14px bold)
```

<task type="auto">
  <name>Task 1: Mobile-Layout, Safe-Areas und schwebende Farb-/Größen-Trigger</name>
  <files>app.html</files>
  <action>
    1. Viewport-Meta erweitern: `viewport-fit=cover` ergänzen.

    2. Im :root CSS Safe-Area-Variablen einführen, z. B.:
       --safe-top: env(safe-area-inset-top, 0px);
       --safe-bottom: env(safe-area-inset-bottom, 0px);
       --safe-left: env(safe-area-inset-left, 0px);
       --safe-right: env(safe-area-inset-right, 0px);

    3. .app-Grid auf min-height: 100dvh; und padding-top/bottom/left/right gegen die Safe-Insets schützen — ODER (besser für Topbar/Pagebar): die jeweiligen Bars selbst `padding-top: var(--safe-top)` / `padding-bottom: var(--safe-bottom)` und `--toolbar-h` / `--pagebar-h` als reine Inhaltshöhe behalten, sodass die effektive Bar-Höhe = Inset + Inhalt ist.
       Konsequenz: `grid-template-rows: calc(var(--toolbar-h) + var(--safe-top)) 1fr calc(var(--pagebar-h) + var(--safe-bottom))`.
       Sidebar bekommt `padding-left: var(--safe-left)` und Footer-Bereich `padding-bottom: var(--safe-bottom)`.

    4. Mobile-Breakpoint (≤ 768 px):
       - Topbar bleibt einzeilig (kein flex-wrap, kein zweiter Row).
       - #btn-mobile-color und #btn-mobile-size aus dem Topbar-Fluss entfernen — entweder per CSS `position: absolute` oder per HTML-Verschiebung in einen neuen Container `.mobile-quick-tools` direkt unterhalb der Topbar. Variante CSS-only ist vorzuziehen, wenn ohne HTML-Restruktur möglich.
       - Container/Buttons positionieren: `position: absolute; top: calc(var(--toolbar-h) + var(--safe-top) + 8px); right: calc(8px + var(--safe-right)); display: flex; flex-direction: column; gap: 8px; z-index: 50;`
       - Sicherstellen: nicht über zweite Topbar-Reihe gerendert (die fällt weg), nicht unter andere Sidebar/Modal-Elemente.
       - Auf Desktop bleiben sie wie bisher (also nur die mobile-spezifischen Trigger betroffen — die Klassen `.mobile-color-trigger` / `.mobile-size-trigger` sind dafür der Anker).

    5. Auf Mobile nicht nötige Topbar-Elemente prüfen — wenn die zweite Reihe wegfällt, sicherstellen dass die Topbar nicht overflowt; ggf. existierende Mobile-Media-Queries vereinfachen.

    Avoid: Inhalts-Layout über JS umzubauen (alles via CSS); 100vh statt 100dvh (auf Mobile unzuverlässig durch Browser-Chrome); Hard-coded Pixel-Insets statt env().
  </action>
  <verify>
    - DevTools iPhone-Profil: Topbar einzeilig, Color/Size-Buttons rechts oben, kein Inhalt unter Notch.
    - Code-Grep: `grep -n "viewport-fit\|safe-area-inset" app.html` zeigt neue Regeln.
    - Manuell: Topbar-Inhalt wraps nicht; Canvas füllt Mittelbereich.
  </verify>
  <done>AC-1 + AC-2 erfüllt.</done>
</task>

<task type="auto">
  <name>Task 2: Touch-Target-Größen und Text-Kontrast anheben</name>
  <files>app.html</files>
  <action>
    1. Touch-Target-Audit für alle interaktiven Klassen:
       - `.tool-btn`: aktuell durch `--toolbar-h: 48px` schon ≥44px hoch — Breite kontrollieren (`min-width: 44px`).
       - `.footer-btn`, `.nb-add-btn`, `.page-btn`, `.bg-btn`: `min-width: 44px; min-height: 44px;` setzen wo nicht erfüllt.
       - Notebook-Listen-Einträge (`.nb-item` o. Ä.): Mindesthöhe 44 px sicherstellen, Hover-Icons (rename/delete) mindestens 32 px Hit-Fläche; auf Touch ist Longpress weiterhin der primäre Pfad.
       - Padding nicht aufblähen, wo Container das Target-Größe schon liefert.

    2. Kontrast-Pass an Color-Tokens:
       - `--text-faint` von #3e3b56 auf einen Wert mit ≥3:1 Kontrast gegen --bg (#0e0d15) anheben — Zielbereich z. B. #6c6886 oder #7a7692. Verifizieren mit https://webaim.org/resources/contrastchecker oder Formel.
       - `--text-dim` von #7a7692 auf ≥4.5:1 anheben (für Body-Text). Zielbereich z. B. #a8a3c2.
       - Konkrete Werte vor Commit kurz validieren: APCA oder klassisch WCAG.
       - Falls einzelne Stellen mit `--text-faint` semantisch wirklich "fast unsichtbar" sein sollen (Placeholder, Disabled), unverändert lassen oder neue Variable `--text-disabled` einführen.

    3. Disabled-States: Buttons mit `disabled`-Attribut sollten weiterhin sichtbar reduziert sein (opacity ~0.4 reicht), aber nicht durch dunkle Color-Tokens unkenntlich.

    Avoid: Globaler Text-Größen-Bump (würde Layout brechen); Border-Radius/Visuelle-Identität-Änderungen außerhalb der Skala dieses Plans.
  </action>
  <verify>
    - Stichprobe je Button-Klasse in DevTools messen: Computed-Box-Größe ≥ 44 × 44 px.
    - Color-Tokens manuell durch Contrast-Checker prüfen: --text-dim / --bg ≥ 4.5:1, --text-faint / --bg ≥ 3:1.
    - Visuelle Kontrolle: zuvor schwer lesbare Sidebar-Texte und Sub-Labels jetzt klar lesbar.
  </verify>
  <done>AC-3 + AC-4 erfüllt.</done>
